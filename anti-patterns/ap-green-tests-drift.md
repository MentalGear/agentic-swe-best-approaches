# Green tests, drifted behaviour

Reports of agent work that passed its gates and was still wrong:

- **A replatforming that kept the suite green.** bunderbunder was brought in on a large system ported to a
  new platform with coding agents, declared operational "in record time". Then: the promised
  scalability didn't arrive (it got worse), telemetry could no longer be trusted, and users stopped
  trusting the outputs. Their diagnosis: the agent "scrupulously kept existing automated tests passing",
  but "any behavior that wasn't explicitly covered by a test was free to change any which way"
  ([49879158](https://news.ycombinator.com/item?id=49879158)). They add that the gains sought could have
  come from incremental changes removing a few well-known performance anti-patterns; the project began
  when the lead asked their agent "What's the best way to X" and got "a trendslop answer" about a more
  scalable technology, and time pressure did the rest.
- **Each commit fine, the whole wrong.** fingerlocks: while the agent worked on a render pipeline, a
  backing data buffer was "effectively duplicated with a different ABI", as if it had forgotten how to
  query meshes and rebuilt the plumbing. "Every single commit in isolation looks perfect"
  ([49879009](https://news.ycombinator.com/item?id=49879009)).
- **Both models swore it was perfect.** username_my1 set two models to a loop (pick an issue, develop,
  QA) with a separate "CTO" checking architecture. Both said nothing was lacking; the software then wrote
  large amounts of data to CSV files instead of the database, because the agent had used CSV for testing
  and drifted ([49878551](https://news.ycombinator.com/item?id=49878551)).
- **Reviewers of both kinds missed it.** mywittyname: a major production issue because an LLM wrote queries
  against dev databases, "very obviously" labelled as such; "AI reviewer didn't catch it, neither did the
  human reviewer" ([49881705](https://news.ycombinator.com/item?id=49881705)).
- **Silent data loss.** an0malous: the agent allowed a silent failure that would have deleted all of the
  users' data without anyone noticing ([49881067](https://news.ycombinator.com/item?id=49881067)).
- **Bad code tests don't reach.** troupo: the recurring case is "to get a record from a database read all
  records from it, and filter in memory", which passing tests won't catch unless you already know to look
  ([49881965](https://news.ycombinator.com/item?id=49881965)); asveikau has seen tests that look complete
  but "doesn't actually test anything" ([49880019](https://news.ycombinator.com/item?id=49880019)).

## Why the gate lies

Tests encode what someone thought to check. Everything else (observability, data shape on the wire, indexes,
what happens on failure) is unowned. A reviewer who reads each diff sees a plausible change; the drift
is in the sum. layer8 makes the general point: testing and fuzzing complement but don't substitute for
reasoning about the code ([49879394](https://news.ycombinator.com/item?id=49879394)); mckn1ght: the
requirements, or the DSL tests are generated from, still need human verification
([49881662](https://news.ycombinator.com/item?id=49881662)).

## Fixes people suggest

- Pin behaviour first: characterisation tests or a running original as an oracle before changing anything
  ([wf-port-with-oracle](../workflows/wf-port-with-oracle.md)).
- Check the non-functional contract on purpose (telemetry, performance, data shape), not just the
  functional suite ([wf-executable-quality-rules](../workflows/wf-executable-quality-rules.md)).
- After unattended runs, read the result as a whole, not commit by commit (fingerlocks' point).
- Ask "what's the smallest change that gets the benefit?" before accepting a rewrite as the plan
  ([wf-second-research-pass](../workflows/wf-second-research-pass.md)).
