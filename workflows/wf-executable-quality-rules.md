# Turn "what good looks like" into checks the agent runs

eithed: "If you can quantify quality/reliability/understandability, you can tell LLM what kind of code do you
expect. If not, you get whatever." Their team's stack ([49879687](https://news.ycombinator.com/item?id=49879687)):

- automated tests, static analysis, and a pattern matcher for problematic code (a "static rector");
- **architecture tests** that define relationships between application layers;
- **ADRs** describing how new code should be written and existing code treated, for humans and agents;
- **acceptance criteria as documents** (Gherkin) that an agent can read to check whether the code does what
  it was meant to.

Their claim: "what code should do" is preached but rarely defined, so everyone's idea of quality differs
slightly and only existing code aligns people; written down, an LLM can write to the patterns, review
against them, and check acceptance criteria. They also give it reference works because it otherwise
applies a different pattern each time (self-report).

## Related practices

- askonomm gives the agent code-coverage data, architecture analysis, test requirements and "gotcha's a
  competent engineer would know" about the system, and keeps coming up with the solutions themself
  ([49879190](https://news.ycombinator.com/item?id=49879190)).
- monkpit: it's "common advice to wire in deterministic feedback"; static languages aren't inherently
  better for LLMs, they give compiler results ([49880672](https://news.ycombinator.com/item?id=49880672)).
  zamalek: languages with stronger type safety are "a massive crutch" for LLMs
  ([49882531](https://news.ycombinator.com/item?id=49882531)). Two views of the same lever.
- westurner: 100% branch coverage isn't sufficient; add fuzzing, formal methods or TLA+ where warranted;
  always verify a candidate solution against the criteria; and agents sometimes reimplement what the code
  already does instead of refactoring, so bloat needs an explicit deletion step
  ([49879693](https://news.ycombinator.com/item?id=49879693)). They point to a tool that checks an agent's
  claims against the git diff (listed in [tool-mentioned-unvetted](../tools/tool-mentioned-unvetted.md)).
- pu_pe: the mission-critical industries the article cites rely on extensive testing for assurance, with
  human review a layer on top ([49879149](https://news.ycombinator.com/item?id=49879149)).

## Limits

Checks only verify what somebody encoded ([ap-green-tests-drift](../anti-patterns/ap-green-tests-drift.md)),
and the tests need a human to confirm they test the right thing (mxey: "Who writes those tests and makes sure
they test the right thing", [49878822](https://news.ycombinator.com/item?id=49878822); mckn1ght,
[49881662](https://news.ycombinator.com/item?id=49881662)).
Steps to adopt: start with the rule you re-explain most often in review, make it a failing check, then
tell the agent to run the checks before it reports done.
