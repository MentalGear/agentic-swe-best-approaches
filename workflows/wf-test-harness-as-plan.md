# End-to-end tests that carry the plan

orisho's workflow for large changes ([49854300](https://news.ycombinator.com/item?id=49854300)):

1. Have the model write an **HTML explainer** of what will be built, with code snippets. It serves as
   the source of truth; models "have no issue using that HTML artifact".
2. Before execution, **interactively build an end-to-end test** that includes pieces of the plan.
   *When a test fails, the relevant part of the plan is in the error message.*
3. Let it run. They report 12h routinely and up to 48h unattended (11h of API time) "with good
   results" — one person's anecdote.
4. At each check-in, have it append current state to the HTML, blog-style (append-only), then
   iterate on the tests and their messages.

## Why it works

The plan lives where the agent looks when it's lost: the failing test. Related practices:
Fr0styMatt88 locks down liked behaviour with tests while prototyping
([49852784](https://news.ycombinator.com/item?id=49852784)); wildzzz builds a test suite at each
milestone ([49852661](https://news.ycombinator.com/item?id=49852661)); frankc: make systems
verifiable and deterministic so agents can write strong property-based tests
([49852511](https://news.ycombinator.com/item?id=49852511)).

## Steps to adopt

- Write assertions with messages like `"Plan §3.2: orders over the limit must be rejected with 422"`.
- Keep the plan sections numbered so messages can cite them.

## Measured loops, and what tests can't show (second thread, 2026-09-28)

CuriouslyC, on frame hitches in a game: the agent had moved preloads to a loading screen and left the rest
compiling in the main loop. They told it to build a speculative pre-warming queue with a per-frame budget,
then had it run fully headed games and chase every frame over 16 ms until a batch showed fewer than 1 in
1000 such frames and none over 60 ms after settling. "The approach, the metrics, the validation system and
the loop" were the human's contribution ([49880656](https://news.ycombinator.com/item?id=49880656)). The pattern: a numeric done-criterion the agent can
run itself.

efficax goes further, asking the model to build a fuzzer and property tests, run every scenario and log full
traces ([49878532](https://news.ycombinator.com/item?id=49878532)). Pushback: shallow tests that "doesn't actually test anything" (asveikau,
[49880019](https://news.ycombinator.com/item?id=49880019)); "you have just shifted the problem of verification elsewhere" (boomlinde, [49881359](https://news.ycombinator.com/item?id=49881359));
testing isn't understanding (layer8, [49879394](https://news.ycombinator.com/item?id=49879394)); the generated tests still need reviewing
(lolakutty, [49880199](https://news.ycombinator.com/item?id=49880199)). See [ap-green-tests-drift](../anti-patterns/ap-green-tests-drift.md) and
[wf-executable-quality-rules](wf-executable-quality-rules.md).
