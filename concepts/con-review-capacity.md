# Review capacity is the limit on agent output

The article's "old trick": make the change massive and it gets merged on trust. Commenters describe the
same dynamic from inside teams.

## The squeeze

- whatever1: "I cannot review your 5,000 lines of code you produce per day vs the 100 you were
  producing before" ([49878472](https://news.ycombinator.com/item?id=49878472)). rfgplk says 5,000 is
  slow and has seen repos doing 100k-250k lines of change per week
  ([49878599](https://news.ycombinator.com/item?id=49878599)); whatever1's reply: those teams "are not
  even pretending to be reviewing the code" and an LLM reviewer "will find a nitpick while ignoring the
  huge fire in the core of the design" ([49878762](https://news.ycombinator.com/item?id=49878762)).
- askonomm: with the volume, review "is effectively dead in the water"; some companies have AI review
  AI-written code ([49878390](https://news.ycombinator.com/item?id=49878390)).
- paimapi: executives expect 3-5x velocity while review and testing become the bottleneck, and the
  platform/SRE people who could build faster review tooling are the ones cut
  ([49879308](https://news.ycombinator.com/item?id=49879308)).
- mywittyname approved two PRs in one day "so large they break github"
  ([49881512](https://news.ycombinator.com/item?id=49881512)).
- patorjk: a large visualization PR looked fine; a colleague noticed the repo already used recharts,
  which does 90% of it ([49879879](https://news.ycombinator.com/item?id=49879879)). Plausible-looking
  output hides duplicated capability.

## What people propose instead of reading everything

| Approach | Who | Caveat |
|---|---|---|
| Agents review too; humans do less and less | bitwize [49879739](https://news.ycombinator.com/item?id=49879739); Zardoz84 says AI review "catches errores [sic] made by the AI coding agent" but is not deterministic [49878540](https://news.ycombinator.com/item?id=49878540) | See the dispute in [con-cross-model-review](con-cross-model-review.md); mywittyname reports neither the AI nor the human reviewer caught queries written against dev databases ([49881705](https://news.ycombinator.com/item?id=49881705)) |
| Shift to scope-setting and verifying correctness | munksbeer: "Even traditional code reviews are going to go away" [49880628](https://news.ycombinator.com/item?id=49880628) | brazukadev expects hand-coders who understand the system to be the most requested ([49881125](https://news.ycombinator.com/item?id=49881125)) |
| Tests are the critical layer; human review sits on top | pu_pe: mission-critical industries rely on extensive testing, with review "far from the most critical" layer [49879149](https://news.ycombinator.com/item?id=49879149) | palmotea: some places are abolishing formal QA because of LLMs ([49879257](https://news.ycombinator.com/item?id=49879257)). See [ap-green-tests-drift](../anti-patterns/ap-green-tests-drift.md) |
| Encode the rules so checks run automatically | eithed [49879687](https://news.ycombinator.com/item?id=49879687) | [wf-executable-quality-rules](../workflows/wf-executable-quality-rules.md) |
| It is still better than the humans' code | empath75 would "rather commit claude written code from lazy and incompetent developers than code that they wrote" [49878758](https://news.ycombinator.com/item?id=49878758) | Doesn't address volume |

Marha01 asks for data before anyone claims either side, such as bug density of human versus AI code
over time ([49878719](https://news.ycombinator.com/item?id=49878719)); no one in the thread supplied it.

## Use it

Treat reviewer attention as a budget the agent spends. Cap diff size per change, route human reading to
the parts tests can't judge (data model, API shape, failure behaviour), and move the rest to checks that
run without a person ([wf-executable-quality-rules](../workflows/wf-executable-quality-rules.md)).
[wf-review-code-not-plans](../workflows/wf-review-code-not-plans.md) assumes you can afford the review.
