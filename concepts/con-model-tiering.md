# Plan with a strong model, build with a cheaper one

- dgrin91: on a limited budget, plan with the top model and implement with a cheaper one; "I feel like
  this saves cost in the end" ([49852895](https://news.ycombinator.com/item?id=49852895)).
- jmb99: plan with the expensive model, implement with a cheaper one, with small validation calls
  back up ([49852421](https://news.ycombinator.com/item?id=49852421)).
- esafak: value in "a separate, smarter model for planning than execution" and persisting the plan
  for audit ([49850915](https://news.ycombinator.com/item?id=49850915)).
- Claude Code's `opusplan` model setting does this split (diegof79 calls it "barely documented",
  [49851420](https://news.ycombinator.com/item?id=49851420)); see [tool-opusplan](../tools/tool-opusplan.md).
- The inverse also appears: philbo picks *smaller, faster* models deliberately because short loops
  with a human thinking matter more than raw capability ([49853739](https://news.ycombinator.com/item?id=49853739)).

## Use it

The plan must be self-contained for this to work: the cheaper model gets the file, not the
conversation. That makes [wf-plan-file-fresh-session](../workflows/wf-plan-file-fresh-session.md)
a prerequisite.

## Later in the thread (refresh 2026-09-26)

- cogman10: plan and split into tasks with Opus, implement with DeepSeek; "saves a bunch of money and
  is fast" ([49856567](https://news.ycombinator.com/item?id=49856567)).
- Huppie's orchestrator is instructed to pick the right (usually cheaper) model per subtask and do
  little itself ([49857325](https://news.ycombinator.com/item?id=49857325)).
- james2doyle uses plan mode as protection when trying unfamiliar cheap models: "the last thing I
  want [is] to allow file edits and destructive tool calls" ([49859085](https://news.ycombinator.com/item?id=49859085)).
